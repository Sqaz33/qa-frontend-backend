# Postman: вход, токен и права доступа

## Два вопроса сервера
Аутентификация: кто отправил запрос? Авторизация: разрешено ли этому пользователю выполнить действие?

В учебном API без действующего токена защищённые запросы получают 401. С действующим токеном обычного пользователя доступ к отчёту получает 403. Это правила нашего контракта: в других системах, например для скрытия существования чужого объекта, возможен 404.

Стенд: http://127.0.0.1:8766, версия auth-demo-1.0. Основной demo-1.0 остаётся на 8765. Этот отдельный API исправный; итоговая практика с неизвестным дефектом ещё впереди.

## 1. Переменная и папка
В существующем QA Local добавь authBaseUrl=http://127.0.0.1:8766. Не заменяй baseUrl. В своей коллекции создай папку «Авторизация»; её запросы пока настраивай по одному, не меняя auth всей старой коллекции.

## 2. Профиль без входа
Создай GET {{authBaseUrl}}/api/me. Authorization → No Auth, Body → none, Scripts пустые.
Save → Send. Ожидание: 401 и {"error":"unauthorized"}.
Если Authorization уже задан вручную в Headers, убери его: No Auth не удаляет вручную введённые заголовки.

## 3. Вход
POST {{authBaseUrl}}/auth/login.
Authorization → No Auth. Body → raw → JSON:

```json
{
  "username": "qa_user",
  "password": "Study123!"
}
```

Это вымышленные данные для локального упражнения. Content-Type: application/json.
Scripts → Before request:

```javascript
pm.collectionVariables.unset("authAccessToken");
```

Scripts → After response:

```javascript
pm.test("Вход выполнен: 200", () => {
    pm.response.to.have.status(200);
});

const data = pm.response.json();

pm.test("Выдан Bearer-токен", () => {
    pm.expect(data.access_token).to.be.a("string").and.not.empty;
    pm.expect(data.token_type).to.eql("Bearer");
});

if (pm.response.code === 200 &&
    typeof data.access_token === "string" &&
    data.access_token.length > 0) {
    pm.collectionVariables.set("authAccessToken", data.access_token);
}
```

Save → Send. Ожидание: 200, access_token, token_type=Bearer, expires_in=900 и user с username=qa_user, role=user. Перед входом очищаем старое значение, чтобы ошибочный вход не оставил рабочий токен от прежнего пользователя.

Только для учебной ручной цепочки временно сохраняем выданный токен в переменную коллекции. Не экспортируй его в Git/файлы и не публикуй логи с ним. Для реальных секретов используй Vault; для временного токена внутри одного Runner-прогона подходит pm.variables.set без сохранения в коллекцию.

## 4. Профиль с токеном
Создай второй GET {{authBaseUrl}}/api/me, например «Профиль с токеном», чтобы сохранить отрицательный запрос из шага 2.

Authorization → Bearer Token. В поле Token:

```text
{{authAccessToken}}
```

В этом поле не пиши слово Bearer: Postman добавит его в Authorization сам.
Ожидание: 200 и {"id":1,"username":"qa_user","role":"user"}.
Тело GET не требуется. Токен передаётся заголовком, пароль повторно не отправляется.

## 5. Доступ без нужной роли
GET {{authBaseUrl}}/api/admin/report с тем же Bearer Token.
Ожидание: 403, error=forbidden. Пользователь распознан, но его роль не позволяет читать отчёт.

Затем можно войти отдельным запросом с username=qa_admin и тем же учебным паролем. Сохрани полученный токен тем же способом и повтори отчёт: ожидается 200. Менять роль в JSON запроса входа недостаточно — роль определяет сервер.

## 6. Выход
POST {{authBaseUrl}}/auth/logout с текущим Bearer Token, Body none → 204 без тела.
С тем же токеном GET /api/me → 401 invalid_token. Здесь проверяется серверный отзыв токена; одно удаление переменной в Postman ещё не доказывает выход на сервере.

## Что проверять
- Правильные данные входа; неверный пароль; неизвестный пользователь.
- Отсутствующий, выдуманный, истёкший и отозванный токен.
- Доступ обычного пользователя и администратора к одному защищённому действию.
- Профиль принадлежит тому пользователю, который вошёл.
- Пароль и хеш не возвращаются.
- Вызов API напрямую соблюдает права независимо от видимости кнопки в интерфейсе.

## Срок жизни и формат
Токен действует 15 минут; по истечении выполни вход снова. После перезапуска стенда нужен новый вход. В этом API нет refresh-токена и автоматического обновления.
Здесь непрозрачная случайная строка, не JWT. Bearer описывает способ предъявления токена, а не его внутренний формат.
