# HTTP: запрос, ответ и поиск ошибки

**На повторение: 5 минут.** Материал объяснён; самостоятельная практика ещё впереди.

## Кто за что отвечает

| Часть | Что делает в обычном web-приложении |
|---|---|
| Frontend | Показывает интерфейс, обрабатывает действия, отправляет запросы и отображает ответы |
| Backend | Проверяет данные и права, выполняет правила продукта, работает с хранилищем и другими сервисами |
| База данных | Хранит данные; браузер обычно обращается к backend, а не напрямую к базе |
| API | Интерфейс взаимодействия программ; здесь через него frontend обращается к backend |

Серверная ошибка может возникать в самом приложении, его зависимостях или инфраструктуре. Деление на front/back — начало исследования, а не всегда готовая причина.

## Из чего состоит запрос

Вымышленный пример создания учебной заявки:

```http
POST /api/applications
Content-Type: application/json

{"amount": 50000}
```

- **Метод** POST — в этом API создаём заявку.
- **Путь** /api/applications — к какому ресурсу обращаемся.
- **Заголовки** — метаданные; Content-Type описывает формат тела.
- **Тело** — передаваемые данные, здесь сумма.

Query-параметры находятся после вопросительного знака: `/api/applications?status=new` — например, фильтр списка. Это отличается от JSON-тела.

Назначение методов по контракту: GET — получить; POST — создать или выполнить операцию; PUT — задать состояние; PATCH — частично изменить; DELETE — удалить.

## Как выглядит ответ

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 71, "amount": 50000, "status": "new"}
```

Это иллюстрация, а не результат проверки стенда.

Проверяем статус, заголовки, тело и фактический результат операции. Успешный статус не доказывает правильность суммы и сохранения данных.

| Статус | Что означает |
|---|---|
| 200 | Запрос обработан успешно |
| 201 | Ресурс создан |
| 204 | Успех без тела ответа |
| 400 | Ошибка запроса |
| 401 | Нет подходящих данных аутентификации |
| 403 | Доступ запрещён |
| 404 | Ресурс не найден |
| 500 | Внутренняя ошибка сервера |

Конкретные ожидаемые статусы задаёт API-контракт: какие запросы допустимы, какие поля нужны и какие ответы должны приходить.
4xx не означает автоматически дефект frontend. 5xx не указывает конкретную причину сбоя.

## Где искать ошибку

Условие примера: сумма передаётся и отображается в рублях. Пользователь ввёл 50000, а на экране после создания увидел 5000.

| Наблюдение | Направление проверки |
|---|---|
| В запросе уже amount=5000 | Как frontend считал значение и сформировал запрос |
| Запрос содержит 50000, ответ — 5000 | Backend, его зависимости и обработка данных |
| Ответ содержит 50000, экран показывает 5000 | Как frontend обработал и отобразил ответ |

Для локализации записываем всю цепочку: ввод → запрос → ответ → интерфейс.
Прямой повтор запроса в Postman помогает отделить поведение API от интерфейса. Отличия авторизации, окружения и данных нужно учитывать.

## Как работает HttpOnly-cookie

Сервер устанавливает cookie через Set-Cookie. В следующих подходящих запросах браузер сам добавляет заголовок Cookie. JavaScript не обязан читать значение.
Если это идентификатор сессии, сервер по нему находит сессию и связанного пользователя.
Если это токен, сервер проверяет его по принятой в приложении схеме.

## Формулировка для интервью

> Сопоставлю действие пользователя с запросом, ответом и отображением. Если данные меняются уже при формировании запроса, исследую frontend. Если прямой API-запрос даёт неправильный результат, проверяю серверную часть и её зависимости. Вывод подтвержу конкретными данными.

## Частые ошибки

- Смотреть только на код ответа.
- Делать вывод о backend только по сообщению на экране.
- Сравнивать запросы из разных окружений или от разных пользователей, не учитывая различия.
