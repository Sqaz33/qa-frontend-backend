# Клиент-серверная архитектура и REST

**На повторение: 5 минут.** Теория на учебном примере; новых проверок в этом блоке не выполняли.

## 1. Клиент, сервер и данные

В нашем web-приложении:
- Клиент — браузер с frontend. Показывает форму, принимает ввод, отправляет запросы, отображает ответы. Postman тоже клиент, но вместо интерфейса сайта мы сами собираем запрос.
- Backend — серверная программа. Проверяет данные и права, выполняет правила продукта, обращается к хранилищу и другим сервисам.
- База — хранит заявки. В demo-1.0 это SQLite.

Логическая цепочка: клиент → HTTP API backend → база → backend → клиент.
Это три роли; они не обязаны работать на трёх разных компьютерах. Наш пример работает локально.

Двухзвенная схема может выглядеть как клиент → сервер БД, трёхзвенная — клиент → сервер приложения → БД. В обычном web-приложении браузер обращается к серверу приложения.
Backend может быть монолитом или состоять из сервисов. Монолит развёртывается как одно приложение; микросервисы — отдельные сервисы с собственными обязанностями. Распределённость добавляет сетевые взаимодействия и возможные отказы зависимостей. Архитектура реального продукта работодателя неизвестна.

## 2. Что произошло в твоей проверке

1. В Postman отправлен POST с amount=999.
2. Backend независимо от формы проверил сумму.
3. Получен 422 и fields.amount.

На допустимой границе 1000 ты получил id=4 и подтвердил совпадение данных при чтении. Это пример проверки взаимодействия клиента, API и хранения; прямого исследования БД не было.

## 3. Что такое REST

REST — архитектурный стиль взаимодействия компонентов. Он задаёт ограничения для устройства API и обмена сообщениями.
HTTP — протокол, JSON — формат данных. Их использование само по себе не доказывает соответствие REST.

Ресурс — объект, с которым работаем: заявка, пользователь, документ. Не обязательно строка таблицы.
URI идентифицирует ресурс, например /api/applications/4.
JSON в ответе — представление данных ресурса.

## 4. Ресурсы и методы

| Запрос | Назначение |
|---|---|
| GET /api/applications | Получить список |
| GET /api/applications/4 | Получить заявку 4 |
| POST /api/applications | В нашем контракте — создать заявку |
| PUT /api/applications/4 | Создать или заменить состояние ресурса по этому адресу |
| PATCH /api/applications/4 | Применить частичное изменение |
| DELETE /api/applications/4 | Удалить ресурс из доступных по этому адресу |

PUT, PATCH и DELETE — общие примеры. В demo-1.0 они не реализованы.
POST не ограничен созданием: точную операцию описывает контракт.
При PUT различают замещаемое клиентом состояние и поля, которыми управляет сервер.

Path: /applications/4 — конкретный ресурс.
Query: /applications?status=new — пример фильтра списка в API, которое поддерживает такой параметр.
Body: {"amount":1000} — данные операции.
Headers: Content-Type, Accept, Authorization — формат, предпочтения ответа, данные авторизации.

## 5. Ограничения REST

| Принцип | Смысл |
|---|---|
| Client-server | Разделение обязанностей клиента и сервера |
| Stateless | Запрос самодостаточен; сервер не полагается на сохранённый контекст диалога клиента |
| Cache | Ответы обозначены как допускающие или запрещающие повторное использование из кеша |
| Uniform interface | Общие правила работы с ресурсами, представлениями и сообщениями; в строгом REST — также ссылки на дальнейшие действия |
| Layered system | Между клиентом и конечным сервисом могут быть посредники |
| Code on demand | Необязательная возможность передавать исполняемый клиентом код |

Stateless не запрещает хранить заявки в БД.
GET /applications/4 явно указывает ресурс. Серверу не нужно помнить, какую заявку этот клиент «выбрал» предыдущим вызовом.
В защищённом API каждый запрос также несёт нужные данные аутентификации, например токен.
Обычная схема входа с серверной сессией и строгий REST stateless — разные архитектурные вопросы; сам факт наличия cookie не определяет соответствие REST.

## 6. Идемпотентность

Одинаковый повтор имеет тот же предусмотренный эффект над ресурсом, что и один вызов.
GET, PUT и DELETE идемпотентны по HTTP-семантике. Ответы при этом могут отличаться.
Пример DELETE: первый вызов удалил ресурс, второй получил 404; итог в обоих случаях — ресурса нет.
POST не гарантирует идемпотентность. В нашем демо каждый корректный POST создаёт новую заявку.
PATCH зависит от операции: «установить сумму 1000» и «увеличить сумму на 1000» по-разному ведут себя при повторе.

GET — безопасный метод: он не предназначен для изменения бизнес-данных. Запись технического лога возможна.

## 7. Что из этого нужно QA

Проверять адрес и метод, формат запроса, поля, права, ответы, сохранение данных, повторные вызовы и обработку ошибок.
По цепочке запрос → серверный ответ → отображение искать место расхождения.
Ожидания брать из требований и контракта, а не из того, как случайно ответила реализация.
