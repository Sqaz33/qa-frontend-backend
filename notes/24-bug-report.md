# Баг-репорт: описать проблему так, чтобы её смогли повторить

## Когда есть основание для отчёта
Есть наблюдаемое расхождение между ожидаемым и фактическим результатом. Ожидание берём из требования, контракта или согласованного правила. Если правило неоднозначно, зафиксируй наблюдение и уточни ожидание.

422 на запрещённую сумму — ожидаемый отказ. FAILED из-за неправильного ожидания в скрипте — ошибка теста. Ни один из этих признаков сам по себе не доказывает дефект приложения.

## Что нужно читателю
| Поле | Что написать |
|---|---|
| Заголовок | Условие/действие и конкретный неправильный результат |
| Окружение | Стенд, сборка; для web — браузер и версия, если значимы |
| Предусловия | Пользователь, роль, исходное состояние, данные |
| Шаги | Краткая последовательность, достаточная для повторения |
| Ожидаемый результат | Что должно случиться и по какому правилу |
| Фактический результат | Что действительно произошло |
| Влияние | Какую задачу это мешает выполнить, какие данные затронуты |
| Severity / priority | Предварительная оценка с обоснованием по правилам команды |
| Доказательства | Запрос, ответ, id/время, скриншот, логи, request id при наличии |
| Воспроизводимость | Только реально выполненные попытки и условия |

Часть полей баг-трекер заполняет автоматически. Не нужно вручную дублировать автора, дату и номер, если это уже сделано инструментом. Число полей зависит от команды и задачи.

## Вымышленный пример для разбора
Это иллюстрация, не найденный дефект наших стендов и не результат ученика.

**Заголовок:** «После создания заявки на 50 000 API чтения возвращает сумму 5 000».

**Правило:** при создании сумма должна сохраняться без изменения.
**Окружение:** в реальном отчёте указать проверенные адрес и сборку; здесь они не выдуманы.
**Данные:** корректное имя, amount=50000, consent=true.

**Шаги:**
1. Отправить POST /api/applications с указанными данными.
2. Взять id из ответа.
3. Выполнить GET /api/applications/{полученный id}.

**Ожидание:** в GET amount=50000.
**Факт в условии примера:** в POST отправлено 50000, в GET получено 5000.
**Влияние:** пользователь/оператор получает неверную сумму заявки.
**Доказательства для реального отчёта:** оба фактических запроса и ответа, полученный id, версия и время.
**Воспроизводимость:** здесь не измерена; запись «3 из 3» не добавлять.

## Локализация без догадок
Наблюдение: расхождение получается при прямом обращении к API, без интерфейса.
Вывод: проблема воспроизводится в API-сценарии и не зависит от отображения суммы в браузере.
Что пока неизвестно: где именно возникло изменение — обработка записи, хранение, чтение, зависимость или другой этап. GET сам по себе не показывает содержимое базы.

Не писать «неправильный тип столбца БД», если нет подтверждения.
Не ждать полного понимания причины, чтобы сообщить воспроизводимую проблему. Для блокирующего или серьёзного инцидента важно быстро передать факты и дополнить отчёт по мере исследования.

## Типичные слабые формулировки
- «Заявки сломаны» → какое действие, какие данные, что произошло?
- «Не работает иногда» → при каких условиях и сколько попыток реально выполнено?
- «Как на скрине» → текстовые шаги и результаты всё равно нужны.
- «Бэкендер ошибся» → описать наблюдаемое поведение, убрать обвинение.
