# Ретест и регрессия: как выбирать проверки

## Сначала определить цель
**Ретест (confirmation testing)** — проверить, устранена ли исходная проблема. В зависимости от риска повторяем все проверки, упавшие из-за дефекта, и добавляем варианты, необходимые для проверки исправления. Оригинальные шаги из баг-репорта — отправная точка.

**Регрессия** — проверить возможные нежелательные последствия изменения. Она может затронуть сам изменённый компонент, соседние функции и другие системы через общие зависимости.

Это цели тестирования. Ретест не обязательно ручной, а регрессия не обязательно автоматизированная.

## Подготовка к проверке
- Убедиться, что нужная сборка развёрнута на нужном стенде.
- Понять, что изменили: обработку поля, общий валидатор, хранение, API-контракт или интерфейс.
- Подготовить исходные данные и роль; сохранить идентификаторы проверяемых объектов.
- Выполнить подходящий smoke, чтобы проверить доступность критичных функций. GET /health подтверждает доступность этого endpoint, а не всего бизнес-сценария.
- Если smoke выявил блокировку, зафиксировать её и определить, какие проверки заблокированы. Независимые проверки иногда можно продолжить.

## Вымышленный пример
Ранее разбирался условный дефект: отправили сумму 50000, GET вернул 5000. Это не обнаруженный дефект наших исправных стендов.

После исправления путь POST → GET с суммой 50000 — основа ретеста. Дальше выбираем связанные проверки. Ниже план, все проверки пока не выполнены:

| Что проверить | Зачем | Ожидание |
|---|---|---|
| Исходный сценарий с 50000 | Подтвердить исправление | Сумма не меняется в POST/GET |
| 1000 и 100000 | Не нарушены включительные границы | Обе суммы принимаются и читаются без изменения |
| 999 и 100001 | Правка не отключила ограничения | 422, новая запись не создаётся |
| "1000", null, true как amount | Не появилась нежелательная конвертация типов | 422, новая запись не создаётся |
| GET списка и GET по id | Разные способы чтения согласованы | Сумма одной заявки совпадает |
| Отображение в форме/списке UI после чтения | UI правильно использует изменённые данные API | Исходная сумма отображается без искажения |

Дополнительно проверить имя и согласие, если меняли общий валидатор полей. Другое поведение приложения не добавляем автоматически: нужна связь с изменением или продуктовым риском.

Ожидания сверяем с контрактом учебного продукта. Регрессия не обязана всегда содержать ровно эти значения или такой набор.

## Как найти связанные области
1. Посмотреть описание изменения, связанную задачу, при необходимости diff.
2. Уточнить у разработчика, какие компоненты и общие функции затронуты.
3. Проверить контракты и зависимости: кто создаёт, читает и использует изменённые данные.
4. Выбрать случаи, которые могут обнаружить вероятные и серьёзные последствия.
5. Записать оставшийся непроверенный риск.

Ответ разработчика помогает, но QA сопоставляет его с требованиями, известными дефектами и поведением продукта. Общая библиотека может затронуть далёкий экран; близость в интерфейсе сама по себе не доказывает зависимость.

## Если времени мало
Сначала критичные сценарии, риск потери/искажения данных и нарушения доступа, общие изменённые компоненты, исходный дефект и важные границы. Частота использования — один из факторов, но редкая операция тоже может иметь тяжёлые последствия.

Сообщи команде:
- что проверено и на какой сборке;
- какие проблемы найдены;
- что не проверено и почему;
- какое влияние может иметь оставшийся риск.

Сокращение набора по рискам — осознанное решение, не основание записать «проверено всё». Даже весь выбранный набор зелёный не доказывает отсутствие всех дефектов.

## Что записать в результате
Используй templates/retest-regression.md.
Для ретеста: исходный баг, версия, данные, ожидание, факт и доказательства.
Для регрессии: выбранная проверка, связь с изменением, ожидание, факт/статус. Статусы Passed, Failed, Blocked, Not run должны различать реальные результаты и невыполненную работу.

Если исходная проблема остаётся, переоткрыть отчёт с доказательствами. Новый отдельный дефект при регрессии обычно оформить отдельно и связать с изменением. Успешный ретест сам по себе не подтверждает готовность всего релиза.

## Для интервью
«Сверяю сборку, выполняю ретест исходного дефекта. Объём регрессии определяю по затронутым компонентам, их потребителям и рискам. Проверяю основные сценарии, важные границы и негативные случаи. В отчёте отдельно указываю выполненное, найденные проблемы и непроверенные области».

Самостоятельная практика на исправленной сборке ещё предстоит. Матрица выше — учебный план, не журнал выполненных проверок.
