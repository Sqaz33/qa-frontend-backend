# Postman: функция проверки и намеренный FAILED

**На повторение: 3 минуты.**

## Что получилось
На скриншоте ученика видны 201 Created и Test Results 3/3 PASSED: статус, сумма 1000 и положительный целочисленный id.
Раздел скриптов в его приложении называется After response. Before request соответствует Pre-request в документации.

## Что поправить
В третьем pm.test выражение pm.expect передано вторым аргументом напрямую.
JavaScript вычисляет такое выражение до вызова pm.test.
По документированному API вторым аргументом должна быть функция с логикой проверки:

```javascript
pm.test("Выдан положительный целочисленный id", () => {
  pm.expect(
    Number.isInteger(data.id) && data.id > 0
  ).to.eql(true);
});
```

Функция () => { ... } позволяет Postman выполнить утверждение как часть именованной проверки и отнести к ней результат.
При ложном утверждении вне функции возможна ошибка скрипта до регистрации соответствующего теста. Три зелёные строки на одном успешном ответе не проверяют этот случай.

## Увидеть FAILED на практике
Тело запроса оставить с amount=1000.
После исправления третьего теста временно заменить второй тест:

```javascript
pm.test("Демонстрация FAILED: ожидаем 999", () => {
  pm.expect(data.amount).to.eql(999);
});
```

Сохранить и отправить запрос.
Ожидание: HTTP 201, два PASSED и один FAILED, поскольку фактическое 1000 отличается от ожидаемого 999.
Пользователь подтвердил: «failed го дальше». Отдельный скриншот и точное число прошедших проверок не предоставлены.

## Что это означает
HTTP-статус сообщает результат обработки запроса сервером.
Assertion проверяет конкретное ожидание тестировщика.
Здесь сервер получает корректные данные, а ожидание в тесте намеренно неверное. Это упражнение на работу проверок, не обнаруженный дефект API и не запрос с недопустимой суммой.

После наблюдения вернуть второй тест к названию «Сумма — число 1000» и ожиданию .to.eql(1000).
Любой новый успешный POST создаёт отдельную заявку; id может изменяться.
