# Postman: негативная проверка типа JSON

**На повторение: 3 минуты.** Следующий ручной запрос; результат ещё не получен.

## Проверяем одно различие
По контракту amount — целое число от 1000 до 100000.

| JSON | Тип | Ожидание |
|---|---|---|
| {"amount":1000} | Число | Допустимое значение |
| {"amount":"1000"} | Строка | 422, ошибка amount |

Оба примера — синтаксически корректный JSON. Во втором нарушен тип поля по контракту, а не синтаксис JSON.
Имена остальных полей и согласие оставляем корректными.

## Создать отдельный запрос
В собственной коллекции создать «04 — Сумма строкой».
POST {{baseUrl}}/api/applications.
Body → raw → JSON:
```json
{
  "name": "test",
  "amount": "1000",
  "consent": true
}
```
Content-Type application/json; Authorization No Auth.
Before request оставить пустым: этот негативный запрос не должен очищать id ранее созданной корректной заявки.

## After response
```javascript
pm.test("Неверный тип отклонён: 422", () => {
  pm.response.to.have.status(422);
});

const data = pm.response.json();

pm.test("Получена ошибка валидации", () => {
  pm.expect(data.error).to.eql("validation_error");
});

pm.test("Ошибка относится к amount", () => {
  pm.expect(data.fields).to.have.property("amount");
  pm.expect(data.fields.amount).to.be.a("string").and.not.empty;
});
```

Сохранить и отправить.
Ожидание: HTTP 422, ошибка fields.amount и три PASSED.

## Почему PASSED при 422
В этом сценарии ожидается отказ. Проверка проходит, если сервер правильно отклоняет недопустимые данные.
Ранее FAILED получали намеренно неверным ожиданием суммы; здесь ожидание соответствует контракту.

## Граница покрытия
Эти три утверждения проверяют ответ на недопустимый тип.
Отсутствие изменения данных проверяется отдельным сравнением GET до/после; добавим его в общий прогон.

## Дальше
Разобрать отдельно:
- 400: тело не является корректным JSON.
- 415: неподдерживаемый Content-Type.
Это другие условия отказа, их не смешивать в одном запросе.
