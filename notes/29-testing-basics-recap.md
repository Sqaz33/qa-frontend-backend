# Основы тестирования: повторение перед собеседованием

## Что делает тестировщик
Тестирование помогает оценить качество продукта и риски, обнаружить отклонения и дать команде информацию для решения о выпуске.
Работа включает анализ требований, планирование, выбор проверок и данных, подготовку окружения, выполнение, исследование расхождений и отчёт. Проверять можно и документы до появления работающего кода.

Отладка (debugging) — поиск причины и исправление дефекта. Тестирование и отладка — разные задачи, хотя один человек может заниматься обеими.
QA в широком смысле — работа с процессами обеспечения качества; QC — оценка качества результатов. Тестирование относится к контролю качества. Должность «QA» на практике часто означает и работу тестировщика.

## Чек-лист, тест-кейс, баг-репорт
| Документ | Для чего | Твой учебный пример |
|---|---|---|
| Чек-лист | Кратко перечислить, что проверять, с данными/ожиданиями по необходимости | Имя из одного символа отклоняется |
| Тест-кейс | Подробно задать условия, данные, шаги и ожидаемый результат | POST с именем « ivan », затем GET по выданному id, ожидается «ivan» |
| Баг-репорт | Описать обнаруженное расхождение для воспроизведения и решения | В API amount=99999, в UI той же заявки 100000 |

Чек-лист тоже может содержать ожидаемые результаты; тест-кейс обычно подробнее. Жёсткой универсальной границы нет.
В тест-кейсе различай запланированное ожидание и фактический результат конкретного выполнения.
В отчёте о дефекте: заголовок, окружение/сборка, условия и данные, шаги, ожидание/факт, влияние, severity/priority, доказательства. Воспроизводимость не выдумывать.
Severity — серьёзность последствий, priority — важность исправления в очереди работ.

## «ЧБС»: что известно и что предположено
В присланной вакансии сокращение не раскрыто. Рабочая гипотеза — чёрный, белый и серый ящик; подтверждения от автора нет. Не выдавай расшифровку за установленный стандарт.

| Подход | На чём строятся проверки | Пример |
|---|---|---|
| Чёрный ящик | На ожидаемом поведении и требованиях, без опоры на внутреннее устройство | По контракту проверить допустимые/недопустимые данные API |
| Белый ящик | На структуре программы, коде и путях выполнения | По ветвлениям функции спроектировать тесты и измерить покрытие ветвей |
| Серый ящик | Используется частичное знание внутреннего устройства | Учесть известную схему хранения/взаимодействия компонентов при выборе проверок |

Открытый DevTools или Postman сами по себе не делают проверку белым/серым ящиком. Важно, на каких знаниях построены тесты.
Твоё сравнение UI и API по контракту не требовало чтения кода.

## Разные классификации отвечают на разные вопросы
| Классификация | Смысл |
|---|---|
| Функциональное | Делает ли система то, что требуется: создание/чтение заявки |
| Нефункциональное | Характеристики работы: производительность, удобство, надёжность, безопасность и другие |
| Позитивное / негативное | Допустимые условия / недопустимые условия и обработка ошибок |
| Статическое / динамическое | Анализ без запуска проверяемого объекта / проверки с его выполнением |
| Ручное / автоматизированное | Кто/что выполняет действия и сравнение результата |
| Smoke | Короткая оценка основных возможностей сборки, позволяющая решить, можно ли продолжать проверки |
| Ретест | Проверка устранения исходного дефекта |
| Регрессия | Проверка нежелательных последствий изменения |

Один тест может одновременно быть функциональным, позитивным, системным, ручным и построенным по чёрному ящику.
Нагрузочное тестирование исследует работу под заданной нагрузкой; стрессовое — при выходе за обычные/допустимые условия, длительное — поведение во времени. Это не просто повторить много Send без модели нагрузки и критериев.

## Уровни тестирования
- Компонентный: отдельная функция/модуль, например валидатор.
- Интеграция компонентов: взаимодействие внутренних частей, например сервиса и слоя хранения.
- Системный: поведение продукта в целом относительно системных требований.
- Интеграция систем: взаимодействие приложения с другой самостоятельной системой.
- Приёмочный: удовлетворяет ли продукт согласованным потребностям/критериям приёмки.

В сокращённой классификации обе интеграции нередко объединяют в «интеграционное». Не путай уровень с видом теста: функциональность и производительность можно проверять на разных уровнях.
Участие QA и распределение проверок зависят от команды, а не только от названия уровня.

## Как выбирать данные: тест-дизайн
- Классы эквивалентности: разбить данные на группы с ожидаемо похожей обработкой и выбрать представителей. Это сокращает набор, но не гарантирует одинаковость всех скрытых дефектов.
- Граничные значения: проверить разрешённые границы и значения рядом с ними; знать включительность границ и шаг.
- Таблица решений: проверить сочетания условий и соответствующие результаты, например заполненность полей и согласие.
- Переходы состояний: разрешённые/запрещённые переходы, когда такие состояния заданы требованиями.
- Исследовательское тестирование: изучение, проектирование и выполнение проверок идут вместе, с целью и фиксацией наблюдений.

Для примера имени 2–50 символов: отдельно рассмотреть пустое/отсутствующее/нестроковое значение, короткое, допустимое и длинное имя; длины у границ. Правило обрезки пробелов проверить отдельно.

## Ожидаемое и фактическое
Ожидание берётся из требования/контракта/согласованного правила. Факт — из выполненной проверки.
Твоё найденное расхождение: ожидалось отображение 99999, на скриншоте показано 100000. Значения 9999 и 99999 в соответствующих разделах исходного баг-репорта были описаны неточно — это ошибка документации, отдельная от ошибки продукта.
При неоднозначном требовании сначала зафиксируй вопрос и договорённость.

## Верификация и валидация
Верификация: соответствует ли результат заданным требованиям?
Валидация: подходит ли продукт для реальных потребностей и использования?
Они не равны жёстко «только статическое» и «только динамическое».

## Как работа складывается в цикл
Понять требования → оценить риски/объём → выбрать проверки и данные → подготовить стенд → выполнить → исследовать расхождения/описать дефекты → проверить исправление и связанные риски → сообщить результаты и ограничения.
В реальном процессе этапы могут повторяться и идти параллельно.
