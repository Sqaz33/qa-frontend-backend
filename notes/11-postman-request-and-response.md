# Postman: как устроен запрос и где искать ошибку

**На повторение: 4 минуты.**

## Части запроса

| Часть | Пример | Назначение |
|---|---|---|
| Method | POST | Операция по контракту |
| Path | /api/applications/4 | Адрес конкретного ресурса |
| Params | status=new | Query-параметр, если API поддерживает такой фильтр |
| Headers | Content-Type: application/json | Метаданные |
| Authorization | No Auth, Bearer Token и другие | Способ передачи данных аутентификации |
| Body | JSON с name, amount, consent | Данные операции |

В demo-1.0 фильтр status не реализован. Добавление строки в Params само по себе не заставляет сервер фильтровать данные.

## Форматы Body
- raw → JSON: наше API принимает такой формат.
- form-data: части формы, в том числе файлы.
- x-www-form-urlencoded: пары ключ–значение в соответствующем формате.
- binary: содержимое файла как тело.
- none: тела нет; используем для наших GET.

Нельзя поменять только заголовок и ожидать автоматического преобразования формата тела.
Для нашего POST нужен application/json. Неподдерживаемый Content-Type по контракту даёт 415.

## Типы JSON имеют значение

```json
{"amount":1000}
```

Число 1000 допускается.

```json
{"amount":"1000"}
```

Строка "1000" отклоняется по контракту. null и true — тоже отдельные значения, не числа суммы.

Неверный JSON с пропущенной запятой — ошибка синтаксиса и ожидаемый 400.
Корректный JSON с недопустимой суммой — ожидаемый 422.

## Что читать в ответе
Статус, заголовки, тело, фактическое изменение данных.
201 и красивое сообщение не заменяют проверку amount и последующий GET.
Для отрицательного запроса сверять конкретное поле ошибки и отсутствие недопустимой записи.

Одна длительность запроса не доказывает производительность системы под нагрузкой.

## Postman Console
Console помогает увидеть фактически отправленные запросы, перенаправления, ошибки скриптов и console.log.
Если {{baseUrl}} или id подставились неправильно, сначала исследовать разрешённые значения и адрес.
Не выводить пароли и действующие токены в журнал.

## Быстрый порядок расследования
Не отправилось → доступность адреса/порта и ошибка клиента.
404 → путь, id и окружение.
415 → заголовок и формат тела.
400 → синтаксис и контракт.
422 → поля и значения.
Неожиданный 200/201 → сверить тело, данные и смысл операции.
Причину определять по совокупности фактов, а не только по статусу.
