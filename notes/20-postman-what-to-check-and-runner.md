# Что проверять в API и как продолжать работу в Postman

## Откуда брать ожидания
Из требований и API-контракта: какие данные разрешены, какой ответ обещан, что должно измениться. Текущий ответ сервера сам по себе не становится эталоном.

Не нужен одинаковый длинный скрипт в каждом запросе. Выбирай проверки под сценарий и возможную ошибку.

| Что проверять | Пример для создания заявки |
|---|---|
| Статус | Для корректного POST наш контракт обещает 201 |
| Формат ответа | Content-Type application/json, тело разбирается как JSON |
| Структуру и типы | Есть id — положительное целое; amount — число, consent — boolean |
| Значения | Вернулись отправленные name, amount и consent; status=new |
| Бизнес-правила | 1000 допустимо; 999, строка "1000", null и true как сумма запрещены |
| Состояние после запроса | GET по полученному id возвращает созданную заявку |
| Отсутствие побочных эффектов | После отклонённого POST запись не появилась; старые данные не изменились |
| Ошибки | Нужный статус, код ошибки и поле; без внутренних трассировок и чувствительных данных |
| Доступ | На защищённом API: без входа, с неверным/просроченным токеном, с чужими правами |
| Время | Сравнение с согласованным требованием, если оно есть |

В открытом demo-1.0 авторизации нет. Проверки токенов здесь не покажут, насколько правильно устроен контроль доступа. Заголовок Location тоже имеет смысл проверить: наш контракт обещает путь созданной заявки.

Порог «меньше 500 мс» без требования произволен. Один быстрый ответ не заменяет нагрузочное тестирование.

## Сильнее проверки статуса
201 говорит, что сервер сообщил об успехе. Проверка полей говорит, что ответ содержит ожидаемые данные. POST → GET проверяет, что созданный объект доступен через чтение. Доступность через API ещё не доказывает сохранность после перезапуска: это другой сценарий.

JSON Schema помогает проверить форму ответа: обязательные поля, типы, допустимые значения. Она не заменяет сравнение с конкретно отправленной суммой и проверку сохранения. Не запрещай дополнительные поля схемой, если этого не требует контракт.

## Сравнение с запросом
Для запроса с обычным JSON в Body (без переменных):

```javascript
const sent = JSON.parse(pm.request.body.raw);
const actual = pm.response.json();

pm.test("Сумма в ответе совпала с запросом", () => {
    pm.expect(actual.amount).to.eql(sent.amount);
});
```

Сравнение ловит и несовпадение типа: число 1000 и строка "1000" различаются. Оно не доказывает, что сама отправленная сумма допустима: бизнес-правила проверяются отдельно.

## Before request: подготовить данные
На примере отдельного позитивного запроса можно собрать тело до отправки:

```javascript
const payload = {
    name: "Тест " + Date.now(),
    amount: 1000,
    consent: true
};
pm.variables.set("requestBody", JSON.stringify(payload));
```

Body → raw → JSON содержит только:

```text
{{requestBody}}
```

Кавычки вокруг подстановки не нужны: подставляется весь JSON. Date.now() добавляет метку времени для удобства поиска, но не гарантирует уникальность и не защищает от дублей. JSON.stringify сохраняет типы JSON-значений.

В After response ожидаемое тело можно прочитать так:

```javascript
const sent = JSON.parse(pm.variables.get("requestBody"));
const actual = pm.response.json();

pm.test("Сумма совпала с подготовленной", () => {
    pm.expect(actual.amount).to.eql(sent.amount);
});
```

Порядок: подготовка → подстановка переменных и отправка → ответ → проверки и сохранение id.

## Переменные по назначению
- Environment: baseUrl конкретного стенда, например QA Local.
- Collection: общий контекст коллекции; в текущей учебной цепочке так передаётся createdApplicationId.
- Local: временные значения запроса/прогона, например requestBody.
- Iteration data: строка входных данных текущей итерации Runner.

При одинаковом имени приоритет от большего к меньшему: local → iteration data → environment → collection → global. Для временного id внутри одного прогона тоже можно выбрать local; важно понимать нужное время жизни. Секреты не хранить в Git и не выводить в Console.

## Runner и строки данных
Runner выполняет выбранные запросы в указанном порядке вместе со скриптами. Для цепочки выбирай только нужную папку, а не всю учебную коллекцию: каждый успешный POST создаёт запись.

Пример одной итерации:
1. GET списка — снимок исходных данных.
2. POST с недопустимой суммой — ожидание 422 и fields.amount.
3. GET списка — сравнение с исходным состоянием.

Следующая итерация повторяет всю цепочку с другой строкой данных.

| Итерация | amount | Ожидание |
|---|---|---|
| 1 | 999 | 422 |
| 2 | 100001 | 422 |
| 3 | "1000" | 422 |

JSON-файл удобен для проверки типов: число, строка, null и boolean различаются. Значение читается через pm.iterationData.get("amount"); затем тело собирается JSON.stringify, чтобы сохранить тип.

При 3 запросах и 8 строках выполнятся 24 запроса, если весь прогон завершится без остановки. Число assertions зависит от числа и выполнения проверок, оно не равно числу запросов. В тесте на неизменность списка не должно быть параллельных изменений от других запросов.

Обычный последовательный функциональный прогон не заменяет нагрузочный сценарий с заданной конкуренцией.

## Где искать причину FAILED
Прочитай название и сообщение проверки. В Postman Console проверь фактический URL, заголовки, тело запроса и ошибку скрипта. HTTP 422 может быть правильным ожидаемым результатом. FAILED может означать дефект API, ошибку ожидания, неподходящие данные или настройки стенда.
