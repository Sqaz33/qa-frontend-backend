# Postman: чем отличаются 400, 415 и 422

Ожидания ниже взяты из контракта учебного demo-1.0. У другого API правила могут отличаться: сверяйся с его документацией.

| Проверка | Что отправляем | Ответ demo-1.0 |
|---|---|---|
| Неверное значение поля | Корректный JSON, amount как строка "1000" | 422, validation_error, fields.amount |
| Сломанный JSON | Нет запятой между полями | 400, invalid_json |
| Неподдерживаемый формат | Корректный JSON с Content-Type: text/plain | 415, unsupported_media_type |

## Сейчас сделано
На скриншоте запроса 04 видны 422 и fields.amount. После инструкции открыть Test Results ученик сообщил «все прошли». Тело отправленного запроса в этом кадре не раскрыто; результаты скриптов подтверждены текстом.

## Следующая практика: сломанный JSON
Создай новый запрос «05 — Сломанный JSON» в той же коллекции:
- POST {{baseUrl}}/api/applications.
- No Auth, Before request пустой.
- Body → raw → JSON. Content-Type: application/json.

В теле намеренно нет запятой после name:

```text
{
  "name": "test"
  "amount": 1000,
  "consent": true
}
```

Красная подсветка редактора ожидаема. Не исправляй запятую в этом запросе.

Scripts → After response:

```javascript
pm.test("Сломанный JSON отклонён: 400", () => {
    pm.response.to.have.status(400);
});

pm.test("Причина — invalid_json", () => {
    const data = pm.response.json();
    pm.expect(data.error).to.eql("invalid_json");
});
```

Save → Send → Test Results. Ожидаются 400 и два PASSED. Отправленное тело сломано, но ответ сервера содержит корректный JSON: поэтому pm.response.json() применим к ответу.

## После этого: формат тела
В новом запросе «06 — Неподдерживаемый Content-Type» верни запятую, выбери Body → raw → Text. В Headers проверь единственный активный Content-Type: text/plain; убери ручной application/json, если он остался. Ожидание: 415 и error=unsupported_media_type. Этот шаг пока не выполнен.

## Для собеседования
«Проверяю отдельно синтаксис тела, поддерживаемый формат и допустимость значений. В нашем учебном API это 400, 415 и 422 соответственно. Кроме кода смотрю описание ошибки и проверяю, что отклонённый запрос не создал запись».

Один статус не доказывает корректность всей обработки. Два PASSED выше проверяют только статус и error; отсутствие записи требует отдельного сравнения состояния.
