# 3. API и Postman

Цель: проверять контракт и фактический результат операции.

## Минимум
- GET обычно получает представление ресурса; POST часто создаёт ресурс или выполняет операцию.
- PUT задаёт состояние ресурса по контракту; PATCH изменяет его частично; DELETE удаляет.
- Идемпотентность касается итогового эффекта повторения, а не обязательного совпадения ответов. Конкретное API нужно сверять с контрактом.
- REST — архитектурный стиль, а не просто JSON через HTTP.
- В запросе различать path-параметры, query, headers и body.
- JSON: объекты, массивы, строки, числа, true/false, null. Строка "1000" отличается от числа 1000.

## Статусы как ориентир
200 — успешная обработка; 201 — создан ресурс; 204 — успешный ответ без содержимого.
400 — ошибка запроса; 401 — нет подходящих данных аутентификации; 403 — доступ запрещён; 404 — ресурс не найден.
409 — конфликт; 422 может использоваться для ошибок обработки содержимого запроса.
500 — внутренняя ошибка сервера. Ожидаемые статусы задаёт контракт.

## Практика
1. Создать коллекцию и переменную baseUrl для локального стенда.
2. Выполнить корректное создание заявки, сохранить её id.
3. Получить заявку и сравнить поля с отправленными.
4. Проверить пустое обязательное поле, неверный тип и значения за границами.
5. Проверить несуществующий id.
6. Сопоставить один запрос из интерфейса с запросом Postman.

Для каждой проверки: условия, запрос, ожидаемый статус и результат, фактический ответ, изменение данных.
Один статус 200 не подтверждает правильность операции.
Экспорт коллекции и результаты хранить в evidence/; секреты не сохранять.
